   再经 Ollama `system=` 传一次会重复注入。

## 1. 臂的定义（概念澄清，禁止再合并表述）

| 层 | 臂 | 构造 | ground truth |
|---|---|---|---|
| **描述性** | `full-real` | 上游 fix-commit 的完整 Python 投影 | benign（仅报告可表示性与模型表现，**不**作因果推断） |
| **确认性** | `minimal-real` | security-complete 最小真实修复（**见 §1a 的证据分级**） | **benign** |
| **确认性** | `partial` | 从**同一 minimal-real** 机械移除预先标注的安全关键 hunk | **vulnerable** |
| **确认性** | `placebo` | 同文件、AST/行为中性、**按最终 prompt token 匹配** | **vulnerable** |
| **确认性** | `shuffled` | donor ≠ 目标；**约束匹配（token 匹配）**，非循环取下一个 | **vulnerable** |

- **禁止**写 "partial/minimal-real 第四臂"。
- 确认性四臂 = `minimal-real / partial / placebo / shuffled`（**4 臂**）。
- 描述性层（`full-real`）与确认性层**分母必须分开报告**：
  - 确认性：eligible 数 × 4；
  - 描述性：候选数 × 1（若同时报告四臂草案，则为 × 4 并标明 `DRAFT_TRIPLE_ARM`）。
- **不采用**"13 例 full-real + 1 例 minimal-real"的未分层混合设计。

## 1a. minimal-real 的证据分级与**任务边界**（不得外推）

**最小化的机械性取决于是否存在可执行漏洞 oracle**（codex 指正，采纳）：

| 条件 | 允许的表述 | 证据等级 |
|---|---|---|
| 有上游 PoC / 安全回归测试 | **oracle-driven ddmin**（可机械保证安全完整性） | 高 |
| 无可执行 oracle | 只能称 **reviewer-guided minimization** | 较低 |

- **双 reviewer 判定不等价于运行时安全 oracle**，不得混用表述。
- 需要明示：无可执行 oracle 时，"最小"只是**标注者视角**的最小，不是可证明的最小。

**任务边界（关键限定）**：用 security-critical hunk 选择输入窗口 = **向模型提供
ground-truth localization**。因此本实验的任务限定为：

> **在已给定漏洞位置的条件下判断补丁充分性**（given-location patch sufficiency）。

**不得**外推为"端到端补丁验证能力"或"漏洞定位能力"。论文与对外表述均须带此限定。

## 3. 新增门禁：逐 hunk 覆盖（security-hunk coverage）

> **实现现状（2026-09-11，与代码同步）**
>
> **生命周期（人工标签与动态覆盖严格分离）**
> ```
> critical_hunks.template.json    纯机器身份（无标签、无 coverage）
> critical_hunks.reviewer1.jsonl / reviewer2.jsonl   两位标注者独立标签（互不可见）
> critical_hunks.frozen.json      仲裁后：仅身份 + 最终标签（status=FROZEN_LABELED）
> g0_selection/{cve}.json         冻结的 selection manifest（G0 实际使用的行集合）
> v4_hunk_coverage.json           当前表示的动态覆盖（由 selection 消费而来）
> ```
> **Gate 运行时**由纯函数 `evaluate_coverage_gate(frozen × 当前 coverage)` 按
> **hunk identity**（`sample_id + file + file_status + 双侧 count + 完整 body 的
> LF-normalized SHA`）严格 join；断言 identity 集合完全相等（缺/多/重复均阻断）。
> **绝不复用 registry 内可能过期的 coverage**。
>
> **PARTIAL 门禁（P0-4）**：确认性分析要求
> `SECURITY_CRITICAL × FULL → PASS`；`SECURITY_CRITICAL × PARTIAL/ABSENT → FAIL`
> （PARTIAL 需另走敏感性分析或**单独签名的 override 工件**，不得静默放行）。
> 非关键 hunk 省略允许，但**必须计数并落盘**。
>
> **added 判定**：由**文件状态**判定（`new file mode` / `--- /dev/null`），
> **不是** `old_count==0`——已有文件中的纯插入可能是补丁新增的安全检查，必须按其
> 旧侧插入边界上下文计算覆盖。
>
> **覆盖三分类**：由 G0 冻结的 **selection manifest**（实际纳入的原始行号）计算，
> 故 `PARTIAL` 为**可达状态**。
>
> **当前机械实测**（`v4_hunk_coverage.json`）：
> ```
> FULL = 146     ABSENT = 135     NOT_APPLICABLE_ADDED = 3     PARTIAL = 0
> ```
> 在 frozen registry 就位前，Gate 对任何非 FULL 一律保守阻断（`mechanical_absent_samples`）。

对每个候选样本、每个 real-patch hunk，报告其 **vulnerable 行范围**在表示中的覆盖：

```
FULL    / PARTIAL / ABSENT / NOT_APPLICABLE_ADDED
```

**停止条件（硬）**：

| 情形 | 处置 |
|---|---|
| security-critical hunk 的 vulnerable 位置 = `ABSENT` | **不得进入确认性分析** |
| security-critical = `PARTIAL` | 仅可进敏感性分析，或经 reviewer 明确批准 |
| 普通非关键 hunk 被预算省略 | 允许，但**必须计数并落盘** |

- 仅 "code_text 非空" **不满足**本门禁。
- `security_critical` 标注须由协议/人工录入（`v4_hunk_coverage.json` 已留字段）。
- 现状：`ABSENT=138`（5 样本）→ 表示策略必须先修正，否则确认性样本会被大幅削减。

## 4. 长度匹配口径（替代 A4b 的"做不到则逐例报告"）

- **匹配对象 = 确认性 `minimal-real` 的最终 prompt token**（**不是** `full-real`）。
- 比值界 `[0.8, 1.25]`，用**未舍入**原始比值判定。
- `placebo`：按最终 prompt token 匹配（不是按补丁 token）。
- `shuffled`：donor 采用**约束匹配**（token 匹配），禁止简单循环取下一个 CVE。
- 匹配失败：**重新生成或预先排除**，二选一；不得带病入组。
