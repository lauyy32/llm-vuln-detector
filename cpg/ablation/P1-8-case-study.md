# P1-8 · 判别与不可判别的案例研究（2026-09-05）

> 目的：给负面结果配机制解释——为什么 3 个 CVE 能被判别、9 个残留双标不能。
> 数据：`corpus_src/<cve>_{vuln,fixed}` 的 vuln→fixed 源码 diff；判别集来自 ST4（跨重建逐字复现）；
> 双标集 = v9 门禁下 CPGEvidence 两端判 vulnerable 的 9 个 CVE（PA1 rule2）。

## 1. 可判别的 3 例（判别集，跨 v9→v10 复现）

| CVE | 仓库 | 目标 CWE | 漏洞 | 补丁做了什么 | 补丁规模 |
|---|---|---|---|---|---|
| **54574** | termux/proot-distro | CWE-61 | 恶意 tar 经 symlink 逃逸写宿主文件 | 新增 `_safe_resolve`：逐跳钳制在 rootfs 内、绝对 symlink 重根、hardlink `linkname` 同样过滤 | +174/−21 |
| **61539** | xorbitsai/inference | CWE-95 | Llama3 tool-call 解析中 `eval()` 导致 RCE | **移除 `eval()` 解析路径**，改为专用解析器（`llama3_tool_parser.py` −77，`utils.py` +1355，测试 −1695） | +1355/−1772 |
| **67435** | Linuxfabrik/lib | CWE-200 / 918 | `fetch()` 跨源重定向时转发凭证头 | 重定向时**剥离凭证头**（`url.py` 单点修复） | +76/−2 |

**共同点**：危险构造被**移除或被就地、自足地替换**。
- 61539：`eval()` 整条路径消失 → "不再有危险调用"是可直接从代码断言的。
- 67435：凭证转发逻辑被剥离 → 危险行为终止。
- 54574：`_safe_resolve` 是**写在切片内、可自证的路径钳制例程**（`realpath` + 逐跳包含校验），模型能在切片内读完并确认其封闭性。

## 2. 不可判别的 9 例（残留双标）

`12482`(keras tar)、`50181`(langroid)、`50558`(penelope tar)、`53502`(thumbor %2e%2e)、`53598`(prompty)、`54785`(gemini-bridge)、`67424`/`67428`(flyto-core)、`73498`(mcp-atlassian)。

**共同点（GT0 已逐样本确认）**：修复形态是"**插入守卫/净化器**"——
危险 sink（`open()`、`httpx`、路径拼接）**仍然留在代码里**，补丁在 sink 前插入项目自定义校验
（`safe_resolve_path` / `enforce_outbound_url` / `validate_safe_path` / `filter_safe_tarinfos` 等）。
要判"已修复"必须验证这个自定义守卫确实能挡住利用路径，而这：
- 对 **CodeQL**：项目自定义净化器不在模型内 → target 污点流**从未被切断**（PA1 rule1=0；ST2 重建后仍 0）；
- 对 **LLM**：守卫是项目特定实现（多为跨函数调用），切片内不可自证 → 无法确认其完备性，且危险 API 仍在 → 两端都判 vulnerable。

## 3. 定量检查：不是"补丁大小"的问题

| 组 | 补丁改动行数（逐例） | 中位数 |
|---|---|---|
| 可判别 3 例 | 195 / 3127 / 78 | **195** |
| 残留双标 9 例 | 16 / 135 / 64 / 73 / 130 / 127 / 369 / 369 / 781 | **130** |

**比值仅 1.5×，且双标组含 369/781 的大补丁、判别组含 78 行的小补丁 → 补丁规模不是判别因子。**
（这一点必须写明：否则会被质疑"只是因为大补丁更容易被识别"。我们检查了，不成立。）

## 4. 机制综合（写进论文 Discussion）

> LLM 在补丁边界上的判别能力**取决于修复的语义形态，而非补丁规模**：
> - **可判别**：修复**移除了危险构造**（`eval()` 路径删除、凭证转发剥离），或插入了一个**切片内自足、可自证的标准守卫**（路径钳制例程）。
> - **不可判别**：修复**保留 sink 并委托给项目自定义净化器**——此时判定"已修复"等价于验证一个跨函数、项目特定的校验逻辑的完备性；CodeQL 因净化器未建模而流不断（证据层盲区），LLM 因守卫不可自证而只能沿用"危险 API 仍在"的直觉，两端同判 vulnerable。
>
> 这与"净化器盲区"主线一致：**瓶颈不在模型容量，而在补丁是否把判定所需的信息显式写进了可验证的形式**。

## 5. 与 CPG/CodeQL 的关系

- 3 例判别**不依赖 CPG 污点证据**（其中 67435 的 target 流在两侧都缺失；61539/54574 的判别来自源码形态）→ 说明"LLM 的少量判别来自代码阅读，而非 CPG 证据"，进一步支持"CPG 不提供判别增益、只提供报警位置"的结论。
- 9 例双标**同时**是 CodeQL 流不断与 LLM 不可自证的交集 → 两类证据在同一批样本上失明，构成"证据层净化器盲区"的互补证据。
