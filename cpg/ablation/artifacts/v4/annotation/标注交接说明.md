## 0. 一句话说明你在做什么

我们在验证一个假设：**LLM 能否在"已给定漏洞位置"的条件下判断一个补丁是否真正修好了漏洞**。

为了做到这一点，我们需要先知道**每个补丁里哪些代码改动是"安全关键"的**——这就是你的任务。
你的标注会决定后续实验里"最小充分补丁"长什么样，所以**准确性比速度重要**。

---

## 1. 你要回答什么

对**每一个 hunk**（补丁中的一个改动块），回答它的**角色**：

| 角色 | 含义 |
|---|---|
| `DIRECT_SECURITY` | **直接**切断漏洞路径 / 引入必要的安全控制（如越权检查、边界校验、协议约束、净化器） |
| `SUPPORTING_REQUIRED` | 本身不直接修复，但**其它 hunk 依赖它才生效**（如先新增工具函数、再在调用点使用） |
| `NON_CRITICAL` | 与安全无关（重构、注释、日志、测试辅助等） |
| `UNCERTAIN` | **证据不足，无法确定** —— 这是**合法且被鼓励**的选项，不要被迫二选一 |

**最重要的一点**：请**先通读该 CVE 的完整补丁**（手册里每个 CVE 开头都给了完整 diff），再看单个 hunk。
一个 hunk 单独看可能"不必要"，但它可能是其它 hunk 生效的前提（**联合依赖**）。

## 2. 每条记录要填的字段

```json
{
  "sample_id": "CVE-2026-xxxxx",
  "hunk_identity": { "...原样保留，不要改动..." },
  "question": "...原样保留...",
  "criticality": "DIRECT_SECURITY | SUPPORTING_REQUIRED | NON_CRITICAL | UNCERTAIN",
  "dependency_group": ["<完整 64 位 hunk_id>", ...],
  "counterfactual": "是 | 否 | 不确定",
  "evidence": "PoC | regression-test | code-reasoning | insufficient",
  "reason": "一句话依据（非空）",
  "reviewer": "reviewer1 或 reviewer2"
}
```

**关于 `dependency_group`**：

- 只能填**完整的 64 位 `hunk_id`**（手册中每条 hunk 都会给出）；
- **禁止**填前缀、简称、文件名或行号；**禁止**填自己（自引用）；
- 只能引用**同一个 CVE** 内的 hunk；
- 没有依赖就填 `[]`（不要留 `null`）。

**关于 `counterfactual`**（反事实检验）：

> 假设**只移除这一个 hunk**、**保留其它全部 hunk**，目标漏洞是否仍然存在？

- 仍然存在 → `是`；不再存在 → `否`；无法判断 → `不确定`。

**关于 `evidence`**（你的判断基于什么）：

- `PoC`：有可复现的漏洞利用；
- `regression-test`：有可运行的安全回归测试；
- `code-reasoning`：纯代码推理（最常见的选项）；
- `insufficient`：证据不足 —— **若你选 `UNCERTAIN`，这里必须是 `insufficient`**。

## 3. 盲态规则（必须遵守）

1. **独立完成**：不要与另一位标注者讨论任何 hunk、任何 CVE。
2. **不参考模型输出**：不要用 LLM 帮你判断（那会污染实验）。
3. **结果私下提交**：你的文件**只发给我**，不要放进任何共享位置、不要给对方看。
4. 遇到拿不准的，**填 `UNCERTAIN`**，不要猜。

## 7. 常见疑问

**Q：`hunk_identity` 到底是什么？**
A：一条 hunk 的**唯一指纹**（含文件、行号、状态、内容 SHA）。它保证你和另一位标注者
标注的是**同一条** hunk。**请勿修改**。

**Q：我可以只标"是不是安全相关"吗？**
A：不行——请区分 `DIRECT_SECURITY` 与 `SUPPORTING_REQUIRED`，这个区分直接影响后续
"最小充分补丁"是否成立。

**Q：看到新增的文件（比如新增了一个适配器/工具模块），怎么标？**
A：**不要根据代码形态**（"新增文件 / 辅助函数 / 调用点"）**直接决定角色**——这三者都可能
是任一角色，也可能共同构成同一个安全控制。请**分别对每个 hunk 应用反事实问题**：

> 移除**这一个** hunk、保留其余补丁，漏洞是否会重新出现？

- 若某个辅助实现**只是为了让另一个安全 hunk 生效**（它自己不改变执行路径）→ 通常考虑
  `SUPPORTING_REQUIRED`，并在 `dependency_group` 里引用它服务的那个 hunk；
- 若某个 hunk **实际把危险路径切换到了安全实现 / 切断漏洞路径** → 通常考虑 `DIRECT_SECURITY`；
- 若两者**联合必要、缺一不可** → 把依赖关系写进 `dependency_group`；
- 若你**无法从代码上区分**哪个承担了阻断作用 → 选 `UNCERTAIN` + `evidence: insufficient`，
  在 `reason` 里写清你的分歧点。

**注意**：不要因为"看起来像安全组件"就一律标 `DIRECT_SECURITY`，也不要因为"只是调用"
就一律标 `SUPPORTING_REQUIRED`。**这两类误判都会让后续"最小充分补丁"不成立。**

**Q：拿不准到底算不算"安全关键"？**
A：填 `UNCERTAIN` + `evidence: insufficient`，并在 `reason` 里写一句你的疑虑。
**这是完全合格的产出**。
