## 四、关键结论

1. **74 主集 9 例语料错误**（此前只发现 4 例 fixed 缺）：新增 54569/54770（vuln 缺）、
   67422/67425/73498（两侧缺）。**"74 主集 0 例未入库可复现"仅指文件可获得性，不等于数据正确**。
2. **vuln 缺是第二类失效模式**：54569/54770 的 vuln 侧缺 modified 文件，此前"vuln 有 fixed 无"的
   单向扫描没扫到（那是扫 fixed 缺，这是 vuln 缺）。说明 `corpus_builder.py` 的静默跳过是**双侧**
   的，只是此前 fixed 侧缺没信号、vuln 侧缺有 signal（但 <30% 未阻断）。
3. **61539 仍是最要命的**：它 fixed 缺 llama3_tool_parser.py（SSRF 修复核心）+ utils.py vuln 缺，
   是论文仅有的 clean 判别正例之一，其"成功"真实性仍待修复复验。
4. **67422（caret.py 两侧缺）需单查**：两侧缺说明该文件在语料 vuln/fixed 都无，但上游 modified——
   可能是提取时双侧 checkout 都失败（ReDoS 修复核心文件），性质等同 fixed 缺。

## 五、失效模式小结（对 corpus_builder 根因的补充）

五态审计比单向扫描多暴露两类：
- **vuln 侧缺**（54569/54770/10692/61539）：`git checkout fix^ -- f` 失败 → missing_vuln 记 signal，
  但 <30% 未阻断 → 入库（signal 里 blocked=false）；
- **两侧缺**（67422/67425/73498）：双侧 checkout 都失败或 added 文件两侧未提取。

二者都印证：**30% 阈值门禁是失效的**（Codex P0-1），须改为 status-aware 零非预期缺失门禁
（`unexpected_missing > 0 → FAIL`），并改 `git show <commit>:<path>` 取 blob。
