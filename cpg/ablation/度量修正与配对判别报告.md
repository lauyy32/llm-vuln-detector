# 度量修正与配对判别：F1 在配对平衡语料上失效，判定在补丁边界近乎不变

> 日期：2026-09-02 ｜ 语料：74 CVE × {vuln, fixed} = 148 版本（配对平衡，正类占比 50.0%）
> 协议：`--modes code`、无公告摘要（主协议）｜ 模型：Ollama `qwen2.5-coder:7b` / `:14b`，temperature=0
> 数据：`seeds/v8_74/results.csv`（7B）、`seeds/v8_74_14b/results.csv`（14B）
> 脚本：`paired_metrics.py`（本报告全部数字的唯一来源）、`b2_complement_stats.py`
> 产物：`paired_metrics_v8_74_7b.json`、`paired_metrics_v8_74_14b.json`、`b2_complement_stats.json`

## 0. 摘要（结论先行）

本报告是一次**自查驱动的度量修正**，起因是核对"LLM 兜底样本数"时发现语料构造与
主指标不匹配。三个结论，按严重程度递减：

1. **F1 不能作为本语料的主指标。** 语料是 74 个 CVE 的 vuln/fixed 配对集，正类占比
   恰好 50%。平凡基线"全判 vulnerable"取得 **F1 = 0.667**，高于本课题报告过的任何
   scorer（历史最高 14B full = 0.365）。此前所有以 F1 排序得出的强弱结论都缺少这一
   对照，必须补上。
2. **对基率不敏感的指标显示所有判定器接近随机。** 平衡准确率 BA ∈ [0.500, 0.514]
   （随机 = 0.500），马修斯相关系数 MCC ∈ [0.000, 0.033]（随机 = 0）。
3. **判定在补丁边界上近乎不变：96%–99% 的 CVE 对，打补丁前后得到完全相同的判定。**
   真正区分出 vuln/fixed 的只有 1–2 个 CVE（判别率 1.4%–2.7%），配对精确二项检验
   p = 0.25–0.50，不显著。

第 3 条是本课题此前未被度量、也未被外部评审指出的核心缺陷：**系统实际在判断
"这段代码是否存在可疑数据流"，而不是"这个版本是否有漏洞"**。机理在 §5：补丁
通常插入净化/校验节点而不切断污点流，因此污点证据在补丁前后同型。

同时，本次自查产出了一个**方向为正的显著结果**（§6）：在补丁验证任务上新增
阴性对照后，7B 模型对"仅注释与版本号"的装饰性补丁 **17/17 全部正确判为未修复**
（配对精确检验 **p = 0.0039**，本课题当时唯一 p < 0.01 的结果；2026-09-05 注：P1-12 v2 后不再唯一）。（口径注记 2026-09-05：
17/17 为 74 主集原始运行；D1 权威口径 15/15，49257/67428 不在 D1 被排除，p 不变。
论文报 15/15。）这否证了"模型
只是看见补丁就说没事"的先验解释，也定位了 LLM 相对纯静态分析的真实增益点——
判断污点路径上的守卫是否充分。但同一实验也暴露 7B 在真实补丁上正确率仅 47%，
且会被含同类净化器的无关补丁误导（4/17）。

**研究定位据此从"更准的漏洞检测器"改为"补丁边界上的判别力研究"**：现有系统
在版本判别维度接近失效（§3），而真正有信号的是净化器充分性判定（§6）。后者
样本量小、能力窄，但方向明确且已有显著证据。

## 1. 问题：F1 奖励过度预测

语料按 CVE 配对构造：每个 CVE 贡献 1 个漏洞版本与 1 个修复版本，故正类占比恒为
50%。在这种构造下 F1 对"多判正类"有系统性偏好：

| 基线 | Precision | Recall | **F1** | 说明 |
|------|-----------|--------|--------|------|
| 全判 vulnerable | 0.500 | 1.000 | **0.667** | 不看代码，恒定输出 |
| 随机（p=0.5，seed=42） | 0.500 | 0.486 | 0.493 | 不看代码，抛硬币 |
| 全判 benign | 0.000 | 0.000 | 0.000 | 不看代码，恒定输出 |
| —— 本课题最优（14B full） | 0.512 | 0.284 | 0.365 | 完整 CPG 证据 + LLM |

"全判 vulnerable"以 0.667 碾压全部真实判定器。这不说明该基线有检测能力——它的
判别力为零（§3 中判别率 0.000）——而说明 **F1 在此语料上不是能力度量**。

> 归因：本课题所有 scorer 都相当保守（Recall 0.03–0.28），F1 的分母被低召回压低；
> 而平凡基线用满召回换取基率精度，在 50% 基率下即可得 0.667。这是度量选择问题，
> 不是实现缺陷。

## 2. 对基率不敏感的指标

补入平衡准确率 BA = (TPR + TNR)/2 与 MCC（两者在随机猜测下分别为 0.500 与 0）：

| scorer | F1 | BA | MCC |
|--------|-----|-----|------|
| CPGEvidenceScorer | 0.330 | 0.507 | +0.016 |
| LocalLLMScorer (7B) | 0.321 | 0.514 | +0.033 |
| LocalLLMScorer (14B) | 0.365 | 0.507 | +0.015 |
| StructuralHeuristicScorer | 0.196 | 0.500 | 0.000 |
| CodeQLBaselineScorer | 0.051 | 0.500 | 0.000 |
| ConfigSigScorer | 0.000 | 0.500 | 0.000 |
| 全判 vulnerable / benign / 随机 | 0.667 / 0.000 / 0.493 | 0.500 | 0.000 |

**全部判定器的 BA 落在 [0.500, 0.514]、MCC 落在 [0.000, 0.033]。** 与随机猜测的
差距在小数点后第二位，且 74 CVE 的样本量无法支撑这种量级的差异。注意 14B 的 F1
最高（0.365）但 MCC 最低（+0.015）——F1 的提升来自更高召回（0.284）伴随更多误报
（FP 20），在对基率不敏感的口径下并未带来判别力增益。

## 3. 配对判别指标：本语料的正确度量

配对设计允许一个不受基率影响的直接度量：**对每个 CVE，判定器能否把漏洞版本与
它自己的修复版本区分开？**

| 结果 | vuln 版本 | fixed 版本 | 含义 |
|------|-----------|------------|------|
| 判别成功 | 标记 | 未标记 | 真正区分了补丁前后 |
| 反向 | 未标记 | 标记 | 判别方向相反 |
| 双标记 | 标记 | 标记 | 无判别力（把修复版也判为漏洞） |
| 双未标 | 未标记 | 未标记 | 无判别力（两个版本都漏检） |

只有"判别成功"与"反向"构成不一致对（discordant）。零假设"判定器无判别力"下，
不一致对中成功数服从 Binomial(n_discordant, 0.5)，据此给出单侧精确二项 p 值
（配对设计的 McNemar 精确检验）。

### 3.1 主协议结果（74 CVE，code 模式，无摘要）

| scorer | 判别成功 | 反向 | 双标记 | 双未标 | 判别率 | 净判别 | 精确 p |
|--------|----------|------|--------|--------|--------|--------|--------|
| CPGEvidenceScorer | 1 | 0 | 17 | 56 | 0.014 | +0.014 | 0.5000 |
| LocalLLMScorer (7B) | 2 | 0 | 15 | 57 | 0.027 | +0.027 | 0.2500 |
| LocalLLMScorer (14B) | 2 | 1 | 19 | 52 | 0.027 | +0.014 | 0.5000 |
| StructuralHeuristicScorer | 0 | 0 | 9 | 65 | 0.000 | 0.000 | 1.0000 |
| CodeQLBaselineScorer | 0 | 0 | 2 | 72 | 0.000 | 0.000 | 1.0000 |
| ConfigSigScorer | 0 | 0 | 0 | 74 | 0.000 | 0.000 | 1.0000 |
| 全判 vulnerable | 0 | 0 | 74 | 0 | 0.000 | 0.000 | 1.0000 |
| 随机（seed=42） | 15 | 15 | 21 | 23 | 0.203 | 0.000 | 0.5722 |

三点必须说清，避免误读：

- **真实判定器方向正确但幅度极小。** CPG 与 7B 的"反向"为 0（没有把修复版判成
  比漏洞版更危险），方向是对的；但不一致对只有 1–2 个，任何检验都无法达到显著
  （p = 0.25 已是 2 个不一致对能取到的最小值）。
- **随机基线的"判别率 0.203"不是能力。** 它的 15 次成功被 15 次反向完全抵消，
  净判别 = 0.000，p = 0.5722。真实判定器净判别为正（+0.014 ~ +0.027）但接近零。
- **平凡基线"全判 vulnerable"判别率恒为 0**（不一致对为 0）。这正是配对判别指标
  优于 F1 的地方：它无法被恒定输出策略刷高。

### 3.2 核心发现：判定在补丁边界上不变

把"双标记 + 双未标"合并，即**打补丁前后判定完全相同**的 CVE 比例：

| scorer | 判定不变的 CVE | 占比 |
|--------|----------------|------|
| CPGEvidenceScorer | 17 + 56 = 73 | **98.6%** |
| LocalLLMScorer (7B) | 15 + 57 = 72 | **97.3%** |
| LocalLLMScorer (14B) | 19 + 52 = 71 | **95.9%** |
| StructuralHeuristic / CodeQLBaseline / ConfigSig | 74 | 100% |
| 随机（seed=42） | 21 + 23 = 44 | 59.5% |

**96%–99% 的 CVE，系统对漏洞版本与修复版本给出完全相同的答案。** 这是本课题
最重要的单条统计：系统输出的信息量集中在"这段代码区域是否存在可疑数据流"，
而"该版本是否已被修复"这一维度几乎没有被捕捉。

## 4. 对既有结论的影响

逐条对照，明确哪些撤回、哪些保留、哪些必须改述。

| 既有表述 | 处置 | 依据 |
|----------|------|------|
| "LLM F1 0.321 / CPGEvidence 0.330，二者相当" | **保留但降级为次要指标** | 数值无误，但须并列平凡基线 0.667 与 BA/MCC |
| "CPG 证据是 LLM 判别的必要条件（A−B = +0.321 F1）" | **必须改述** | A−B 增益是"是否开火"的增益，不是判别力增益；B 组无 taint 时不开火，F1 自然为 0 |
| "14B 优于 7B（0.365 vs 0.321）" | **必须改述** | F1 升高源于召回升高伴随误报升高；MCC 反而由 +0.033 降至 +0.015 |
| "Bandit F1 0.182，LLM 有 2.2× 优势" | **必须改述** | 两者都远低于平凡基线 0.667，"倍数优势"无实际含义 |
| "证据降级时 CPG 归零、LLM 保 0.265/0.351" | **保留** | 该结论是形态内对比（同一 scorer 跨证据形态），不受基率影响 |
| "结构型 CWE 中纯逻辑/状态类超出系统边界" | **保留并强化** | 配对判别显示边界比原判断更窄 |

**唯一未受影响的结论是证据降级鲁棒性（B-2）**：它比较的是同一判定器在不同证据
形态下的表现，属于形态内纵向对比，与正负类比例无关。

## 5. 机理：补丁插入净化器，污点流在补丁前后同型

为什么判定在补丁边界不变？直接检查 CPGEvidence 的 17 个"双标记"CVE
（`b2_complement_stats.py` 从 `b2_74_7b.json` 的 `cpg_full` 字段确定性导出）：

```
CVE-2026-12482 CWE-022   CVE-2026-45019 CWE-918   CVE-2026-49257 CWE-306
CVE-2026-50181 CWE-022   CVE-2026-50558 CWE-022   CVE-2026-53502 CWE-022
CVE-2026-53598 CWE-022   CVE-2026-54574 CWE-061   CVE-2026-54706 CWE-059
CVE-2026-54707 CWE-863   CVE-2026-54785 CWE-022   CVE-2026-59890 CWE-176
CVE-2026-67424 CWE-918   CVE-2026-67425 CWE-201   CVE-2026-67428 CWE-918
CVE-2026-70491 CWE-200   CVE-2026-73498 CWE-022
```

CPGEvidence 的全部 17 个误报都落在这 17 个 CVE 上——也就是说，**它的误报不是
零散噪声，而是系统性地"修复版本仍报漏洞"**。

原因在于修复方式：这些补丁的典型做法是在原有数据流上插入校验或净化
（`safe_tar_extractall` 路径包含性检查、百分号解码后再校验、SSRF 出站 URL 白名单、
重定向剥离包装器等，见 `patch_verify_report.md` 的 rationale 列）。补丁**没有切断**
source→sink 的可达路径，只是在路径上增加了守卫。而 CodeQL 的污点查询在未建模
这些自定义净化器时，两个版本都会报出同一条流。

由此，"流存在"这一证据在补丁边界上不携带信息。判别所需的信号是**净化器是否
存在且充分**，这是一个语义判断，纯结构证据无法给出。

## 6. LLM 增益的真实位置：净化器充分性判定

§5 直接指向 LLM 可能真正不可替代的位置：判断污点路径上的守卫是否足以消除漏洞。
仓库中已有对应任务（`patch_verify.py`，向 fixed 样本注入 vuln→fixed diff），原报告
结论为"误报修复 7 个、判定改善 11/18"。

但该设定存在**未设阴性对照**的方法缺陷：系统提示直接告知"验证该补丁是否完整
消除了公告所述漏洞"，预设了补丁存在，模型的先验答案即为"补丁有效"。原结果
无法区分两种机制：

- **H1（真能力）** 模型读懂补丁内容，确认净化器覆盖污点路径 → 判 benign；
- **H2（提示先验）** 模型只要看到 diff 就倾向判 benign，与内容无关。

为此新增 `patch_verify_control.py`，在**同一系统提示、同一源码与污点切片、同一
温度**下只替换注入的 diff，构成三个实验臂：

| 臂 | 注入内容 | 补丁是否真的修复 | 正确判定 |
|----|----------|------------------|----------|
| `real` | 该 CVE 真实 vuln→fixed diff | 是 | benign |
| `placebo` | 仅注释/空行/版本号的装饰性 diff | **否** | **vulnerable** |
| `shuffled` | **另一个 CVE** 的真实 diff（形似补丁但与本代码无关） | **否** | **vulnerable** |

样本范围为 §5 的 17 个"CPG 双标记"CVE——预先设定的理由是：补丁验证只在静态证据
无法区分补丁前后时才有意义，这 17 个正是该子集，由脚本确定性导出，无人工挑选。

### 6.1 对照结果（7B，17 CVE × 3 臂 = 51 次判定）

| 臂 | n | 判 benign | 判 vulnerable | benign 率 | 正确率 |
|----|---|-----------|---------------|-----------|--------|
| `real`（真补丁，正确答案 benign） | 17 | 8 | 9 | 0.471 | **8/17 = 0.471** |
| `placebo`（装饰性补丁，正确答案 vulnerable） | 17 | **0** | **17** | **0.000** | **17/17 = 1.000** |
| `shuffled`（他人补丁，正确答案 vulnerable） | 17 | 4 | 13 | 0.235 | 13/17 = 0.765 |

配对精确二项检验（同一 CVE 上 real 与对照臂的判定差异）：

| 对比 | 方向一致（real=benign, 对照=vuln） | 反向 | 不一致对 | 精确 p |
|------|-----------------------------------|------|----------|--------|
| real vs placebo | 8 | 0 | 8 | **0.0039** |
| real vs shuffled | 6 | 2 | 8 | 0.1445 |

**结论：H2（提示先验主导）被否证，但只在 placebo 一档达到显著。**

- **placebo 臂 17/17 全部正确判 vulnerable，benign 率 0.000。** 模型面对"仅注释、
  空行、版本号"的装饰性 diff 时无一例外指出补丁无效，理由明确到点：
  "修复补丁仅更新了版本号和添加了维护性注释，未对漏洞点施加有效防护"。
  配对检验 p = 0.0039，是本课题目前唯一一个 p < 0.01 的显著结果。
  → 模型确实在读补丁内容，而非"看见 diff 就说没事"。
- **shuffled 臂 13/17 正确，但 4 例被骗，检验不显著（p = 0.1445）。**
  失效模式高度一致——被骗的 4 例，其捐赠补丁恰好含有与本样本同类的净化器：

  | 样本 | 捐赠补丁来源 | 模型采信的理由 |
  |------|--------------|----------------|
  | CVE-2026-49257 | CVE-2026-50181 | `safe_resolve_path` 确保解析路径不越界 |
  | CVE-2026-50181 | CVE-2026-50558 | `safe_tar_extractall` 防护路径穿越 |
  | CVE-2026-50558 | CVE-2026-53502 | 解码后校验路径位于根目录内 |
  | CVE-2026-67424 | CVE-2026-67425 | denylist 拦截环境变量插值访问 |

  四例全是 CWE-022/918 族内串台：捐赠补丁引入的净化器**名字和语义都像**本样本
  需要的那一个，模型未核对该函数是否真的出现在本样本代码里、是否覆盖本样本的
  污点路径。**这是一个真实且可复现的失效模式：模型对"净化器存在"的识别依赖
  补丁文本的语义相似性，而非补丁与目标代码的绑定关系。**
- **real 臂只有 47% 正确（9 例假阴性）。** 12482 / 45019 / 49257 / 54706 / 54707 /
  54785 / 67424 / 67425 / 67428 在真补丁下仍判 vulnerable。这与 `patch_verify_report.md`
  原报告的"误报修复 7 个 / 改善 11/18"看似矛盾，实为样本选择差异：原报告 18 个样本
  含多个 CPG 本就未报的容易样本，本对照专挑 §5 的 17 个"CPG 对补丁失明"硬样本。
  **在真正需要补丁验证能力的子集上，7B 的正确率不到一半。**

### 6.2 对补丁验证结论的处置

| 原表述 | 处置 |
|--------|------|
| "误报修复 7 个（判定改善 11/18）" | **保留但须标注样本选择偏差**：该 18 样本集含 CPG 未报的容易样本；在 CPG 失明的 17 个硬样本上正确率仅 8/17 |
| "LLM 具备补丁验证能力" | **改述为**："LLM 能识别与漏洞无关的装饰性补丁（17/17，p=0.0039），但在真实补丁上正确率仅 47%，且会被同类净化器的无关补丁误导（4/17）" |
| （原无阴性对照） | **已补**：placebo 与 shuffled 两臂，51 次判定，原始响应留存 |

**净结论：补丁验证方向上 LLM 确有非平凡能力，且该能力是纯污点分析不具备的
（§5 已证污点流在补丁前后同型）；但当前 7B 的水平不足以支撑"补丁验证器"的定位，
其可靠部分仅限于"排除明显无关的补丁"。** 这是一个诚实但窄的结论。

## 8. 诚实边界

- **本报告不推翻实现，只推翻度量。** 所有 scorer 的原始判定未变，变的是评价口径
  与由此得出的强弱结论。
- **样本量限制依然存在。** 74 CVE 下不一致对仅 1–2 个，配对检验无法达到显著；
  要把"净判别为正"做成可信结论，需要把语料扩到不一致对达到两位数的规模
  （`OPEN-DECISIONS.md` #18 已登记，112 个候选未续跑）。
- **配对判别指标本身有边界。** 它要求 fixed 版本确实修好了该漏洞。语料中已剔除
  重构式修复（缺失率 ≥30% 阻断），但仍可能存在"补丁不完整"的样本
  （如 CVE-2026-54785，`patch_verify_report.md` 中 LLM 明确指出其 `_resolve_path`
  未修复）。此类样本的 truth 标为 benign 但实际仍可利用，会压低判别率。该问题
  尚未逐条复核。
- **CodeQL 净化器建模未做。** §5 的机理解释指向一个可行的改进方向：在污点查询中
  显式建模补丁引入的净化器（`isSanitizer`），使 fixed 版本的流被切断。这是把
  判别力从 LLM 侧转回结构侧的路径，尚未实现，也未纳入本报告结论。
