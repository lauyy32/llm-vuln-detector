## 根因（两条独立，均已定位）

1. **磁盘状态 vs git 跟踪状态混淆**：`.gitignore` 忽略 corpus_pairs 后，判断"语料是否齐全"必须
   用 `git ls-files` 而非 `ls`。前代模型漏判，导致 17 例未入库被勘误成"不缺"。

2. **问题 A 根因已定位（2026-09-07）：fixed 侧 `git checkout` 失败静默跳过**。
   `cpg/corpus_builder.py` 276–289 行提取循环中：
   ```python
   for commit, dst in ((fix_commit, fixed_path), (f"{fix_commit}^", vuln_path)):
       cp = run(["git", "checkout", commit, "--", f], ...)
       if cp.returncode == 0:
           if src.exists(): dst.write_bytes(...)
           else: missing_vuln.append(f)      # 命名错，实为 missing_any
       elif commit == f"{fix_commit}^":       # 只处理 vuln 侧失败
           missing_vuln.append(f)
       # ← fixed 侧 checkout 失败：无分支，静默跳过
   ```
   **fixed 侧 `git checkout` 失败时无任何处理**——不写文件、不记信号、不阻断。4 例的 fixed 缺文件
   正是此 bug 的受害者。触发条件：blob:none 过滤克隆 + lazy fetch 超时（90s timeout）导致 checkout
   失败。**代码级佐证**：61539 的 `extraction_signal.json` 只记了 vuln 侧缺 `utils.py`（fixed 侧缺
   `llama3_tool_parser.py` 无记录）；45019/54338 无 signal（fixed 侧失败静默、vuln 侧全成功）；
   10692 的 signal 也只记 vuln 侧缺 `ag.py`。
   → 这是 Hy4 所问的 **(a) 下载失败被静默跳过**，而非 (b) 系统性只存交集。但该 bug 是**对称隐患**：
   任何 fixed 侧 checkout 失败都会静默，故其余案例可能有**尚未暴露**的同类隐患，须全量内容级审计
   覆盖（不只扫"vuln 有 fixed 无"）。
   **修复方向**：fixed 侧 checkout 失败须 fail-closed（记信号 + 阻断）；或改用 `git show <commit>:<f>`
   直接取 blob（不依赖 checkout 工作区状态）。
