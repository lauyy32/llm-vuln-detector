## 3. 与「17/85 缺口」表述的勘误

任务摘要曾称「17/85 缺失 vendored 源码」。经实测全库核查，**该表述不成立**：

- `corpus_pairs/` 中不存在「17 个空源码 CVE」；
- 项目文档中出现的「17」指 **CPGEvidence 双标记（double-flagged）CVE**，属补丁边界
  判别失效机制，已在 `docs/D5-双标机制与门禁.md` 与 `docs/decisions/OPEN-DECISIONS.md`
  完整记载，与「源码缺失」是**两回事**，不应混为一谈。

结论：本课题的真实可复现性缺口为 **3/85 fixed 版本空源码**，而非 17/85。

## 5. 决策（投稿前必须闭合）

两条等价路径，择一执行：

- **(A) 补 vendor**：对 3 个 CVE 在其 `fix_commit` 重新克隆 fixed 版本源码入库；
- **(B) 正式排除**：主集由 85 对调整为 82 对（剔除 3 个 fixed 空 CVE），同步调整
  `paired_stats.json` 的 n 与所有「85 对 / 170 版本」表述，并在论文中显式申报此排除。

无论 A/B，这 3 个 CVE 的 fixed 为空 → 配对判别恒为 `neither`（无判别力），
剔除或补全**不改变**「判别率近随机」的结论（判别成功计数不变），故不影响立论。
推荐先尝试 (A) 补 vendor；若仓库克隆不可行（网络/体积），则采用 (B) 并申报。
