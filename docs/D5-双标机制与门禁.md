# D5 · 17 双标 CVE 的机制重检与 CWE 匹配门禁（OPEN #25，2026-09-02）

> 配套代码：`cpg/ablation/scorers.py`（`CPGEvidenceScorer` 目标 CWE 匹配门禁）
> 配套测量：`cpg/ablation/d5_doublelabel_analysis.py`（精确反事实，无需重跑 CodeQL）
> 结论先行：**原 §8.5「17 双标 = 补丁插入净化器未建模」归因不成立**；17 分为两类，
> 门禁后 17→7，残 7 属 CPG 补丁边界局限，isSanitizer 建模不足以解决。

---

## 1. 原归因（需修正）

`docs/RESEARCH-DESIGN.md §8.5`、`docs/decisions/OPEN-DECISIONS.md #25`、

`cpg/ablation/TASKS-追踪清单.md` 均将 17 个 CPGEvidence 双标 CVE 解释为：

> 真实补丁多为「插入净化器/校验」而**不切断 source→sink 路径**；上游 taint 查询
> 不认识项目自定义净化器，因此补丁前后报出完全相同的流。

该归因暗示「实现 `isSanitizer` 即可消除 17 双标」。本次重检表明**此推断只对极少数成立**。

---

## 2. 重检方法（严谨性闸门）

1. 从 `results.csv`（148 行）抽出 CPGEvidence 双标 CVE（两端均 vulnerable），共 17 个。
2. 用 `dataset.jsonl` 取每个 CVE 的 `truth CWE`（目标 CWE）与 `cwe_predicted`（CPGEvidence
   实际判定的 CWE）。
3. 对 5 个代表 CVE 做本地 `corpus_pairs/<cve>/{vuln,fixed}` 文件 diff，确认补丁形态。

**关键事实**：`CPGEvidenceScorer` 取切片里 `### CWE-XXX` 段的**第一条污点流**作为判定 CWE
（修改前 `scorers.py` L544–550），**完全无视目标 CWE 是否匹配**；而 `StructuralHeuristicScorer`
早已按 `r.get("cwe") == target` 匹配（L115），故后者不双标。双标根因是 **CPGEvidence 的
越界判定**，不是「净化器未建模」。

## 3. 17 个双标的两类机制

| 类别 | 数量 | CVE | 机制 |
|------|------|-----|------|
| **逻辑类越界（logic-scope-leak）** | 7 | 54706(CWE-59)/54707(CWE-863)/49257(CWE-306)/54574(CWE-61)/59890(CWE-176)/67425(CWE-201/522)/70491(CWE-200) | 目标 CWE 为逻辑类（CPG taint 本不可判），但切片里出现**无关的 CWE-022/918 流**（两端都有）→ 两端都被误判 vulnerable。与净化器无关，是 CPG 证据越界。 |
| **taint-CWE 不匹配（taint-mismatch）** | 3 | 67424/67428/45019（目标 CWE-918 SSRF） | 目标为 SSRF，但 `CpgPathSource` 抓到一条 **CWE-022** 路径遍历流（两端都有）→ 误判。净化器未建模无关。 |
| **真·taint 匹配（taint-matched）** | 7 | 12482/50181/50558/53502/53598/54785/73498（目标 CWE-022） | 目标与判定均为 CWE-022，且**两端都含同一条 CWE-022 流**。本地 diff 显示补丁多为「删除不安全 monkeypatch / 加控制流守卫 / 加项目自定义净化器」，**taint 流在两端均不被切断**。 |

→ 仅第三类的极少部分可能与「净化器未建模」相关；**主导机制（前两类 10/17）是 CPG 证据越界
  与切片非判别性**，isSanitizer 建模无法解决。原 §8.5 归因以偏概全。

---

## 4. D5 修法：目标 CWE 匹配门禁（corpus-level，零过拟合）

将 `CPGEvidenceScorer` 对齐到 `StructuralHeuristicScorer` 的既有门禁：

- 仅当检测到的污点流 CWE **等于目标 CWE** 时判 `vulnerable`；
- 检测到污点流但 CWE 与目标**不一致**（逻辑类越界 / taint-CWE 不匹配）→ 显式 `abstain`
  （证据：CPG 污点证据越界，不构成对本 CVE 的判定）；
- 与「per-CVE 调参 / 逐漏洞建模净化器」无关，全语料统一适用，满足研究纪律
  （禁止标签泄漏、禁止 per-CVE overfit）。

此门禁 pair-independent，不依赖配对版本信息，可复现。

---

## 5. 测量结果（精确反事实，推导自 `results.csv`）

`d5_doublelabel_analysis.py` 在既有 148 行上施加门禁，输出：

| 指标 | 门禁前 | 门禁后 |
|------|--------|--------|
| CPGEvidence 双标 CVE 数 | 17 | **7** |
| 双标移除 | — | 10（7 逻辑越界 + 3 taint-CWE 不匹配） |
| 混淆 TP / FP / TN / FN / abstain | 18 / 17 / 57 / 56 / 0 | 7 / 7 / 57 / 56 / 21 |
| BA | 0.5068 | 0.5009 |
| MCC | 0.0159 | 0.0028 |

- 双标由 17→7，移除的 10 个全是「越界判定」（逻辑类 / CWE 不匹配），门禁后转为 abstain。
- **BA/MCC 几乎不变（仍近随机）**：门禁消除的是误导性双标与逻辑类上的偶然 TP，不拯救性能——
  与项目「全部判定器接近随机」结论一致，反而强化其可信度。
- 残 7 仍为双标（真·CWE-022 匹配），需下节所述 pair-aware 判别性证据。

## 6. 残 7：CPG 补丁边界局限（诚实的负面结果）

残 7 个（12482/50181/50558/53502/53598/54785/73498）目标与判定均为 CWE-022，且**两端均含
同一条 CWE-022 流**。其补丁不切断该 taint 流（删除不安全 monkeypatch / 加守卫 / 加项目自定义
净化器），CodeQL 无法在补丁边界区分 vuln 与 fixed。

- **`isSanitizer` 建模不足以解决**：要让 fixed 版本流被切断，须逐漏洞归纳项目自定义净化器
  模式——这等价于 **per-CVE overfit**，直接违反研究纪律（标签泄漏 / 非 corpus-level 规则），
  且即便建模也只覆盖其中极少部分（如 50558 实为删除 monkeypatch，无净化器可建模）。
- **principled 修法（OPEN）**：pair-aware 判别性证据——CPGEvidence 仅在该 CVE 的
  vuln 流与 fixed 流**不同**时才构成判定；两端流完全相同则 abstain（无补丁边界信号）。
  该修法需 (a) 在 harness 中捕获**每版本流集合**（当前 `cpg_slices` 文本仅渲染是否存在流，
  未结构化存储 vuln/fixed 流差异），(b) 将 `CPGEvidenceScorer` 改为 pair-aware。
  风险：若某 CVE 两端流确为同一非判别性流（如 50558 推测如此），pair-aware 门禁会使两端
  均 abstain——**丢失 vuln 真阳**，故须先逐 CVE 验证 vuln 流是否判别性，再决定，不可盲用。

→ 残 7 属 CPG 在补丁边界的**系统性局限**，是本课题「补丁边界判别力研究」定位的实证支撑，
  而非待修缺陷；建议在论文中作为边界声明，而非以 isSanitizer 强行消除。

> **2026-09-03 实测验证（见 `docs/D5-isSanitizer-flowcut.md`）**：通用 stdlib 路径规范化谓词
> （`os.path.realpath/abspath/normpath/...`）对 CWE-022 重跑，`taint.csv` 行数 272→260（切割 12 条
> 无关流），但 CPGEvidence 的 BA/MCC/双标数**完全不变**（BA=0.501、MCC=0.003、双标 9）。假设得证：
> 项目自定义净化器不调用 stdlib 规范化，通用 isSanitizer 无从切断。CPG 在补丁边界的判别上限由
> **flow-cut baserate** 量化 = **5/74 ≈ 6.8%**（74 CVE 中仅 5 个的补丁真的改变了污点流集），
> 直接确立「引入 CPG 不能突破随机」。
