# 研究设计：上下文增强在什么条件下才有效

> 课题：基于大语言模型的上下文增强智能漏洞检测
> 版本：CPG 阶段 v0（研究设计，2026-08-07）
> 作者：lauyy32

## 1. 核心研究问题

不是"LLM 能不能检测漏洞"（VulDeePecker/Devign/LineVul 已被做烂），而是：**给 LLM 喂入什么上下文、在什么粒度、以什么形式，才能增强它对漏洞的判断？这种增强在什么条件下才有效、什么条件下无效甚至负向？**

## 2. 为什么是这个 framing

- 请求侧实验已暴露：结构化上下文在真实数据集上是负向或无效（No-Context F1 99.1% > CoT 98.2%）。直接宣称"加了 CPG 所以更好"经不起推敲。
- 改为**刻画上下文增强有效的边界条件**，更可证伪、更经得住导师和审稿人，也契合我们已发负向结果的诚实风格。

## 3. 实验设计

- **数据集**：真实 CVE 修复前后代码（Devign 真实仓库），禁止 SARD 类合成标注集。
- **三模式消融**：
  - 仅请求：只有 HTTP 请求文本（沿用 v2.4 能力）
  - 仅代码：CPG 文本化切片（AST/CFG/DFG 切片描述）
  - 请求+代码：二者联合
- **基线**：CodeQL 在同数据集上的检测结果（正面对比，非仅引用论文数字）。
- **指标**：按漏洞类型的检出率、误报率；主看「仅代码」相对「仅请求」的增量，以及「请求+代码」是否超过 CodeQL。
- **可复现**：锁本地模型（Ollama），多 seed 取均值，消除 API 漂移（7/24 deepseek-chat 下架教训）。

## 4. 与导师问题三的对应

- **别人是否做过**：CPG 提取成熟（Yamaguchi 2014 / Joern / CodeQL / Devign），但"把 CPG 喂给 LLM"仍在探索，这是我们的切入位。
- **LLM 能否看懂**：LLM 不吃原始图节点，吃图的文本化切片描述；切片压缩策略本身是工程贡献点。
- **是否只需数据不要图**：纯数据流关系（如"用户输入未净化直接进 SQL 查询"）是关键，图的价值在保留这种跨语句依赖，纯 token 序列会丢。
- **相比 HTTP 请求的优势**：HTTP 请求看不到服务端代码，无法判断"这个请求打到这段代码上是否真能利用"；CPG 能区分"形似攻击的正常流量"与"真正触发漏洞的利用"。

## 5. 下一步（执行顺序）

1. **最小 CPG 管线**：选工具 → 对一个真实 CVE 函数提取 AST/CFG/DFG → 转文本切片（不接 LLM，先验证提取正确）。
2. **三模式端点**：在现有 detect 框架上加「仅代码」「请求+代码」两个模式（复用 cot/standard/no-context 基础设施）。
3. **真实 CVE 数据集收集清洗**。
4. **跑三模式 + CodeQL 基线**，出消融表。
5. **锁本地模型重跑，多 seed**。

## 6. 风险与应对

- 掉回"标准集 100%"陷阱 → 强制真实 CVE 数据，禁用 SARD。
- LLM+CPG 未优于 CodeQL → 两种结果都能写，重点在可解释性/零规则维护的增量论证。
- 工具/环境卡壳 → 先 CodeQL（Docker 镜像成熟），Joern 作备选。

## 7. 执行状态（截至 2026-08-08）

§5 路线图中前四项已落地：

1. **最小 CPG 管线** — 原生 CodeQL 2.26.2 CLI 已端到端跑通 AST/CFG/DFG/taint 四查询，切片文本化正确（见 `cpg/README.md`）。
2. **三模式端点** — `cpg/ablation/` 已实现 `POST /api/v1/detect{mode: request|code|both}` + 可插拔 Scorer（StructuralHeuristic / CodeQLBaseline / LocalLLM）。
3. **真实 CVE 数据集** — `cpg/dataset.jsonl`：GitHub Advisory API 分层抽样 16 条 / 跨 11 仓库 / ≤2 条每仓库 / 11 个 CWE 族群；修复前后代码对齐全。
4. **三模式 + 静态基线消融** — 语料库级单数据库（`corpus_db.py`，建库一次 + 6 次自定义 taint 查询 + 1 次官方定向 analyze，按 `<cve>_<version>/` 前缀隔离样本），全量 dataset.jsonl（32 样本版本）已端到端跑通并产出 `results.csv` + `summary.md`。**三类静态基线**并列：① `StructuralHeuristicScorer`（自建 taint，零命中）；② `CodeQLBaselineScorer`（官方定向查询，覆盖 CWE-022/918/020/295 共 10 个查询）；③ `ConfigSigScorer`（配置/结构签名，CWE-295/059/200 精确签名，020/400/444/639/862/863 因基于缺失/无精确签名显式 abstain）。前者在真实语料上零命中，后者仅在 taint 组命中 1 真阳 + 1 误报；`ConfigSigScorer` 实测在 16 个 vuln 版本上零命中（召回 0/16）。

第 5 项（锁本地模型）进行中：

- `LocalLLMScorer` 的 Ollama HTTP 接口已实现（纯标准库，无第三方依赖；Ollama 不可达时自动 abstain，不中断消融）。
- 受"不为本机安装不明软件"约束，本机尚未安装 Ollama，`--with-local-llm` 自动降级为不纳入；模型接入属环境就绪后的下一步。

**关键边界（消融已揭示，均为实证而非推测）**：

- 数据集 11 个 CWE 中仅 CWE-022、CWE-918 属污点可建模类，但**自定义窄 taint 查询在真实语料上实测零命中**（真实漏洞仓库多为非框架化源码，静态数据流盲目）；官方 CodeQL（CWE-022/918）亦仅在 16 个 vuln 版本中命中 1 个（召回 6.25%）+ 1 个误报。
- 其余 9 类（CWE-020/059/200/295/400/444/639/862/863）为逻辑/语义型，CodeQL Python 套件对其多数无成熟查询，静态基线恒 benign；其中 CWE-295/059/200 虽以精确配置签名（证书校验关闭 / 符号链接跟随 / 调试暴露）尝试，仍因真实漏洞为隐蔽逻辑缺陷（如通配符 SAN 匹配、islink 检查旁路、命名空间边界越界）而非显式不安全配置，签名法零命中（0/16）。
- 综上，标准静态分析（含自定义 taint、官方定向查询与配置签名基线三类）在本多样真实 CVE 上近乎失效——这正是 LLM+CPG 语义层要补的盲区，也是本课题"上下文增强有效边界"的核心论证对象，而非工程缺陷。三模式消融中 request/code/both 的区分度将主要来自 `LocalLLMScorer`（待接 Ollama）。
