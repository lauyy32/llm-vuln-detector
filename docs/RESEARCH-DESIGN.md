# 研究设计：上下文增强在什么条件下才有效

> 课题：基于大语言模型的上下文增强智能漏洞检测
> 版本：CPG 阶段 v0（研究设计，2026-08-07）
> 作者：lauyy32

## 1. 核心研究问题

不是"LLM 能不能检测漏洞"（VulDeePecker/Devign/LineVul 已被做烂），而是：**给 LLM 喂入什么上下文、在什么粒度、以什么形式，才能增强它对漏洞的判断？这种增强在什么条件下才有效、什么条件下无效甚至负向？**

## 2. 为什么是这个 framing

- 请求侧实验已暴露：结构化上下文在真实数据集上是负向或无效（No-Context F1 99.1% > CoT 98.2%）。直接宣称"加了 CPG 所以更好"经不起推敲。
- 改为**刻画上下文增强有效的边界条件**，更可证伪、更经得住导师和审稿人，也契合我们已发负向结果的诚实风格。

## 3. 实验设计

- **数据集**：真实 CVE 修复前后代码（Devign 真实仓库），禁止 SARD 类合成标注集。
- **三模式消融**：
  - 仅请求：只有 HTTP 请求文本（沿用 v2.4 能力）
  - 仅代码：CPG 文本化切片（AST/CFG/DFG 切片描述）
  - 请求+代码：二者联合
- **基线**：CodeQL 在同数据集上的检测结果（正面对比，非仅引用论文数字）。
- **指标**：按漏洞类型的检出率、误报率；主看「仅代码」相对「仅请求」的增量，以及「请求+代码」是否超过 CodeQL。
- **可复现**：锁本地模型（Ollama），多 seed 取均值，消除 API 漂移（7/24 deepseek-chat 下架教训）。

## 4. 与导师问题三的对应

- **别人是否做过**：CPG 提取成熟（Yamaguchi 2014 / Joern / CodeQL / Devign），但"把 CPG 喂给 LLM"仍在探索，这是我们的切入位。
- **LLM 能否看懂**：LLM 不吃原始图节点，吃图的文本化切片描述；切片压缩策略本身是工程贡献点。
- **是否只需数据不要图**：纯数据流关系（如"用户输入未净化直接进 SQL 查询"）是关键，图的价值在保留这种跨语句依赖，纯 token 序列会丢。
- **相比 HTTP 请求的优势**：HTTP 请求看不到服务端代码，无法判断"这个请求打到这段代码上是否真能利用"；CPG 能区分"形似攻击的正常流量"与"真正触发漏洞的利用"。

## 5. 下一步（执行顺序）

1. **最小 CPG 管线**：选工具 → 对一个真实 CVE 函数提取 AST/CFG/DFG → 转文本切片（不接 LLM，先验证提取正确）。
2. **三模式端点**：在现有 detect 框架上加「仅代码」「请求+代码」两个模式（复用 cot/standard/no-context 基础设施）。
3. **真实 CVE 数据集收集清洗**。
4. **跑三模式 + CodeQL 基线**，出消融表。
5. **锁本地模型重跑，多 seed**。

## 6. 风险与应对

- 掉回"标准集 100%"陷阱 → 强制真实 CVE 数据，禁用 SARD。
- LLM+CPG 未优于 CodeQL → 两种结果都能写，重点在可解释性/零规则维护的增量论证。
- 工具/环境卡壳 → 先 CodeQL（Docker 镜像成熟），Joern 作备选。
