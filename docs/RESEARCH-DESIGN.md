# 研究设计：上下文增强在什么条件下才有效

> 课题：基于大语言模型的上下文增强智能漏洞检测
> 版本：CPG 阶段 v0（研究设计，2026-08-07）
> 作者：lauyy32

## 1. 核心研究问题

不是"LLM 能不能检测漏洞"（VulDeePecker/Devign/LineVul 已被做烂），而是：**给 LLM 喂入什么上下文、在什么粒度、以什么形式，才能增强它对漏洞的判断？这种增强在什么条件下才有效、什么条件下无效甚至负向？**

## 2. 为什么是这个 framing

- 请求侧实验已暴露：结构化上下文在真实数据集上是负向或无效（No-Context F1 99.1% > CoT 98.2%）。直接宣称"加了 CPG 所以更好"经不起推敲。
- 改为**刻画上下文增强有效的边界条件**，更可证伪、更经得住导师和审稿人，也契合我们已发负向结果的诚实风格。

## 3. 实验设计

- **数据集**：真实 CVE 修复前后代码（Devign 真实仓库），禁止 SARD 类合成标注集。
- **三模式消融**：
  - 仅请求：只有 HTTP 请求文本（沿用 v2.4 能力）
  - 仅代码：CPG 文本化切片（AST/CFG/DFG 切片描述）
  - 请求+代码：二者联合
- **基线**：CodeQL 在同数据集上的检测结果（正面对比，非仅引用论文数字）。
- **指标**：按漏洞类型的检出率、误报率；主看「仅代码」相对「仅请求」的增量，以及「请求+代码」是否超过 CodeQL。
- **可复现**：锁本地模型（Ollama），多 seed 取均值，消除 API 漂移（7/24 deepseek-chat 下架教训）。

## 4. 与导师问题三的对应

- **别人是否做过**：CPG 提取成熟（Yamaguchi 2014 / Joern / CodeQL / Devign），但"把 CPG 喂给 LLM"仍在探索，这是我们的切入位。
- **LLM 能否看懂**：LLM 不吃原始图节点，吃图的文本化切片描述；切片压缩策略本身是工程贡献点。
- **是否只需数据不要图**：纯数据流关系（如"用户输入未净化直接进 SQL 查询"）是关键，图的价值在保留这种跨语句依赖，纯 token 序列会丢。
- **相比 HTTP 请求的优势**：HTTP 请求看不到服务端代码，无法判断"这个请求打到这段代码上是否真能利用"；CPG 能区分"形似攻击的正常流量"与"真正触发漏洞的利用"。

## 5. 下一步（执行顺序）

1. **最小 CPG 管线**：选工具 → 对一个真实 CVE 函数提取 AST/CFG/DFG → 转文本切片（不接 LLM，先验证提取正确）。
2. **三模式端点**：在现有 detect 框架上加「仅代码」「请求+代码」两个模式（复用 cot/standard/no-context 基础设施）。
3. **真实 CVE 数据集收集清洗**。
4. **跑三模式 + CodeQL 基线**，出消融表。
5. **锁本地模型重跑，多 seed**。

## 6. 风险与应对

- 掉回"标准集 100%"陷阱 → 强制真实 CVE 数据，禁用 SARD。
- LLM+CPG 未优于 CodeQL → 两种结果都能写，重点在可解释性/零规则维护的增量论证。
- 工具/环境卡壳 → 先 CodeQL（Docker 镜像成熟），Joern 作备选。

## 7. 执行状态（截至 2026-08-08）

> ⚠️ **本节为 2026-08-08 的阶段快照，其中"16 CVE 语料"与"Ollama 未接入、LocalLLM 恒 abstain"两项已过期；末尾"静态基线失效 → LLM+CPG 补盲区"的推论也已被 2026-09-02 的度量修正部分推翻。当前事实基础与结论请以 §8 为准，本节仅作历史留痕。**

§5 路线图中前四项已落地：

1. **最小 CPG 管线** — 原生 CodeQL 2.26.2 CLI 已端到端跑通 AST/CFG/DFG/taint 四查询，切片文本化正确（见 `cpg/README.md`）。
2. **三模式端点** — `cpg/ablation/` 已实现 `POST /api/v1/detect{mode: request|code|both}` + 可插拔 Scorer（StructuralHeuristic / CodeQLBaseline / LocalLLM）。
3. **真实 CVE 数据集** — `cpg/dataset.jsonl`：GitHub Advisory API 分层抽样 16 条 / 跨 11 仓库 / ≤2 条每仓库 / 11 个 CWE 族群；修复前后代码对齐全。
4. **三模式 + 静态基线消融** — 语料库级单数据库（`corpus_db.py`，建库一次 + 6 次自定义 taint 查询 + 1 次官方定向 analyze，按 `<cve>_<version>/` 前缀隔离样本），全量 dataset.jsonl（32 样本版本）已端到端跑通并产出 `results.csv` + `summary.md`。**三类静态基线**并列：① `StructuralHeuristicScorer`（自建 taint，零命中）；② `CodeQLBaselineScorer`（官方定向查询，覆盖 CWE-022/918/020/295 共 10 个查询）；③ `ConfigSigScorer`（配置/结构签名，CWE-295/059/200 精确签名，020/400/444/639/862/863 因基于缺失/无精确签名显式 abstain）。前者在真实语料上零命中，后者仅在 taint 组命中 1 真阳 + 1 误报；`ConfigSigScorer` 实测在 16 个 vuln 版本上零命中（召回 0/16）。

第 5 项（锁本地模型）进行中：

- `LocalLLMScorer` 的 Ollama HTTP 接口已实现（纯标准库，无第三方依赖；Ollama 不可达时自动 abstain，不中断消融）。
- 受"不为本机安装不明软件"约束，本机尚未安装 Ollama，`--with-local-llm` 自动降级为不纳入；模型接入属环境就绪后的下一步。

**关键边界（消融已揭示，均为实证而非推测）**：

- 数据集 11 个 CWE 中仅 CWE-022、CWE-918 属污点可建模类，但**自定义窄 taint 查询在真实语料上实测零命中**（真实漏洞仓库多为非框架化源码，静态数据流盲目）；官方 CodeQL（CWE-022/918）亦仅在 16 个 vuln 版本中命中 1 个（召回 6.25%）+ 1 个误报。
- 其余 9 类（CWE-020/059/200/295/400/444/639/862/863）为逻辑/语义型，CodeQL Python 套件对其多数无成熟查询，静态基线恒 benign；其中 CWE-295/059/200 虽以精确配置签名（证书校验关闭 / 符号链接跟随 / 调试暴露）尝试，仍因真实漏洞为隐蔽逻辑缺陷（如通配符 SAN 匹配、islink 检查旁路、命名空间边界越界）而非显式不安全配置，签名法零命中（0/16）。
- 综上，标准静态分析（含自定义 taint、官方定向查询与配置签名基线三类）在本多样真实 CVE 上近乎失效——这正是 LLM+CPG 语义层要补的盲区，也是本课题"上下文增强有效边界"的核心论证对象，而非工程缺陷。三模式消融中 request/code/both 的区分度将主要来自 `LocalLLMScorer`（待接 Ollama）。

## 8. 讨论：结论强度、替代解释与研究定位修正（2026-09-02）

本节取代 §7 末尾的推论。支撑数据见 `cpg/ablation/度量修正与配对判别报告.md`、
`paired_metrics_v8_74_{7b,14b}.json`、`patch_verify_control.json`、`b2_complement_stats.json`。

### 8.1 度量口径修正：此前的强弱结论建立在一个失效指标上

语料是 74 CVE × {vuln, fixed} = 148 版本，正类占比恰为 50.0%。在该基率下，平凡基线
"全判 vulnerable"取 P=0.500 / R=1.000 / **F1 = 0.667**，高于本课题报告过的任何真实
判定器。F1 在此奖励过度报警，因此不能承担主指标职责。改用对基率不敏感的平衡准确率
BA（随机 = 0.500）与 Matthews 相关系数 MCC（随机 = 0），并按配对设计计算判别率与
McNemar 精确二项检验。主协议复算结果（`--mode code`）：

| 判定器 | F1 | BA | MCC | 配对判别（正/反） | 净判别率 | McNemar p |
|---|---|---|---|---|---|---|
| StructuralHeuristic | 0.196 | 0.500 | 0.000 | 0 / 0 | 0.000 | 1.0000 |
| CodeQLBaseline | 0.051 | 0.500 | 0.000 | 0 / 0 | 0.000 | 1.0000 |
| ConfigSig | 0.000 | 0.500 | 0.000 | 0 / 0 | 0.000 | 1.0000 |
| CPGEvidence | 0.330 | 0.507 | +0.016 | 1 / 0 | 0.014 | 0.5000 |
| LocalLLM 7B | 0.321 | 0.514 | +0.033 | 2 / 0 | 0.027 | 0.2500 |
| LocalLLM 14B | 0.365 | 0.507 | +0.015 | 2 / 1 | 0.014 | 0.5000 |
| 平凡·全判 vulnerable | **0.667** | 0.500 | 0.000 | 0 / 0 | 0.000 | 1.0000 |
| 平凡·随机(p=0.5) | 0.493 | 0.500 | 0.000 | 15 / 15 | 0.000 | 0.5722 |

**全部判定器的 BA 落在 [0.500, 0.514]、MCC 落在 [0.000, 0.033]。** 按这两个指标，
本课题目前没有任何判定器展现出实质超过随机的能力。原 F1 数值本身无计算错误，但
"LLM 相对 Bandit 有 2.2× 优势"（54 样本口径 F1 0.409 vs 0.182；74 样本主协议下
LLM 为 0.321 / 0.365）这类表述失去意义——两者都远低于不看代码的平凡基线 0.667，
在同一个失效指标上比倍数没有意义。该表述已在 `bandit_report.md` 与
`B3-消融与互补性报告.md` 就地加注失效标记。

### 8.2 回应替代解释一："7B 太弱"

审稿意见指出，B 组（剥离污点证据）LLM 全漏可以用"7B 能力不足"解释，而不必引入
"CPG 证据必要"。这是可检验的命题，模型规模对照给出的答案是**分维度的**：

- **在 B 组绝对检出上，该解释部分成立。** 7B B 组 F1 = 0.000（TP=0），14B B 组
  F1 = 0.073（TP=3, FP=5）。参数量翻倍确实恢复了 3 个语义可判样本，说明存在能力门槛。
- **在补丁边界判别这一核心维度上，该解释不成立。** 7B → 14B：BA 从 0.514 降到 0.507，
  MCC 从 +0.033 降到 +0.015，净判别率从 0.027 降到 0.014（14B 多出 1 例判别方向反转）。
  三项指标**无一改善**。

因此"换个更大的模型就好了"不能消解本课题的负面结果：瓶颈不在推理侧的模型容量，而在
证据侧的信息量（机制见 §8.5）。这一点反而是本课题相对同类工作可辩护的实证——多数
"LLM + 静态分析"工作只报单一模型的 F1，无法区分"方法有效"与"指标虚高"。

### 8.3 回应替代解释二："必要性"应降级

原表述"CPG 污点证据是 LLM 判别的**严格必要条件**"已经历两次降级，现予完全撤回：

1. 第一次（14B B 组）：14B 在无污点证据下恢复 3 个 TP，"严格必要"改为"近似必要"。
2. 第二次（本次度量修正）：A 组优于 B 组的证据本身是 F1，而 F1 在本语料不可用；A 组
   自身 BA ≈ 0.507–0.514，接近随机。因此"A 组显著优于 B 组"不足以支撑必要性主张。

**改述为**：污点证据决定了 LLM 的**报警位置**——14B 剥离污点证据后真阳从 21 降至 3
（ΔF1 = 0.365 → 0.073 = +0.292），即 21 个真阳中 18 个依赖污点证据才成立——但它没有
提升 LLM 的**判别正确性**（BA 0.507，接近随机）。这是"证据引导注意力"，而非"证据构成
判别的必要条件"。

### 8.4 回应"LLM 兜底只有 1 个样本"，并给出全口径交叉表

该批评指向 B-2 报告 §3.1 的"8 个补全样本"。核对结果：该数字的口径是
**54 版本 / 7B / `truncated` 形态 / 弃权型**，原文未标注口径，确实容易被读作全局结论。
现将"LLM 兜底"拆为两型并给出全部组合（`b2_complement_stats.py`，74 版本）：

| 证据形态 | 7B 弃权型 + 纠错型 | 14B 弃权型 + 纠错型 |
|---|---|---|
| `full`（完整证据） | **0** | **3** |
| `sink_only` | 9 | 15 |
| `truncated` | 13 | 20 |

- **弃权型**（CPG abstain、LLM 判 vulnerable）＝确定性解析失效后 LLM 接手，是兜底的主体。
- **纠错型**（CPG 判 benign、LLM 推翻）全部组合中最多仅 3 例（14B：CVE-2026-53656 /
  61539 / 61632）。据此**撤回"LLM 能纠正 CPG 的错误结论"这一表述**，证据不足。
- 批评者引用的"1"很可能来自 `full` 形态（7B 为 0、14B 为 3）。真实答案是：兜底量在
  0–20 之间随（模型 × 证据形态 × 样本规模）变化，**完整证据下互补性近零**，不得以降级
  形态的数字为完整证据背书。B-2 报告 §3.1 已补口径标注、§7 已补全交叉表。

### 8.5 为什么所有判定器都接近随机：机制

**96%–99% 的 CVE 在补丁前后得到完全相同的判定**（CPGEvidence 73/74 = 98.6%，
7B 72/74 = 97.3%，14B 71/74 = 95.9%）。其中 17 个 CVE 上 CPGEvidence 把 vuln 与
fixed **两个版本都**判为 vulnerable——它的 17 个误报全部来自这里，是系统性而非噪声。

机制：真实补丁大多是**插入净化器或守卫**（`safe_tar_extractall`、路径包含性检查、
SSRF 拒绝名单），而**不切断 source → sink 数据流路径**。上游 taint 查询不识别这些项目
自定义净化器，于是补丁前后报出同一条流。LLM 吃的是同一份污点证据加上几乎相同的源码，
因此继承了同样的失明。

这正是 §8.2 的解释：加大模型无效，因为信息瓶颈在证据侧。

### 8.6 唯一方向为正的显著结果：净化器充分性判断

原补丁验证实验在 prompt 中预设"存在补丁"，无法区分"模型读懂补丁内容"（H1）与
"见到 diff 就倾向判 benign"（H2）。补三臂阴性对照（`patch_verify_control.py`，
固定 prompt / 源码 / 污点证据 / temperature = 0，仅替换注入的 diff），子集取上述
17 个 CPG 双标 CVE，7B：

| 臂 | 注入内容 | 期望判定 | 正确 | 配对精确检验 p |
|---|---|---|---|---|
| `real` | 真实修复 diff | benign | 8/17（47.1%） | — |
| `placebo` | 仅注释与版本号的装饰性 diff | vulnerable | **17/17（100%）** | **0.0039** |
| `shuffled` | 另一 CVE 的真实修复 diff | vulnerable | 13/17（76.5%） | 0.1445 |

- **H2 被否证**：模型确实读补丁内容，不是见 diff 即判 benign。p = 0.0039 是本课题目前
  唯一 p < 0.01 的结果。
- **但能力边界很窄**：`real` 臂正确率仅 47%（9 例漏判）；`shuffled` 臂 4 例被含同族
  净化器的无关补丁骗过，且失败模式可复现（49257←50181、50181←50558、50558←53502、
  67424←67425）。
- 综合表述应为：**能识别与漏洞无关的改动，不能可靠判断相关改动是否充分。**

### 8.7 研究定位修正

原定位"上下文增强让 LLM 检测得更准"在本语料上不成立（BA ≈ 随机）。改为：

> **补丁边界上的判别力研究。** 静态污点分析在"补丁是否充分"这一问题上可证明地失明
> （自定义净化器未建模，17/74 双标），这是 LLM 唯一具备独立信息贡献的位置。本课题的
> 贡献是把该子问题隔离出来、给出可证伪的三臂对照协议，并量化 LLM 在其上的真实边界。

### 8.8 关于"新颖性不足"的诚实评估

"把 CPG 喂给 LLM"这一组合本身确实不新。当前可辩护的新颖点不在组合，而在方法论：

1. 指出在配对平衡语料上 F1 会奖励过度报警（平凡基线 0.667），并给出配对判别率 +
   McNemar 精确检验的替代口径——同类工作若只报 F1，可能掩盖判定器接近随机的事实。
2. 补丁验证任务的阴性对照协议（`placebo` / `shuffled`），可直接复用于任何"让 LLM 判断
   补丁是否修好"的工作。
3. 定位并量化静态污点在净化器建模上的系统性盲区（17/74，机制明确、修法明确）。

以上三点是**评测与方法论贡献，不是检测性能贡献**。若目标是性能型论文，当前结果不够；
若定位为评测/负面结果型工作，证据链是完整且自洽的。

### 8.9 尚未关闭的威胁

- **样本量**：不一致对数 n ≤ 3，McNemar 精确检验在该规模下不可能显著（n = 3 最小
  p = 0.25）。需扩语料使不一致对进入两位数（候选池尚有 112 条未跑）。
- **缺确定性对照臂**：CodeQL `isSanitizer` 建模未实现，因此"LLM 在净化器充分性上优于
  静态分析"仍缺同任务的确定性基线对比。
- **规模稳健性未知**：14B 未跑阴性对照，`placebo` 的 p = 0.0039 是否随规模保持未验证。
- **标注可靠性**：`real` 臂 9 例漏判中可能含"补丁本身不完整"的样本（如 CVE-2026-54785），
  需逐例复核 ground truth。
